# Если что-то не запускается

| Симптом | Что сделать |
|---|---|
| `brew` не найден | Установить Homebrew с brew.sh, открыть новый Terminal, повторить `./start.sh` |
| Не удаётся скачать модели | Проверить доступ к GitHub/Hugging Face. Скачайте разрешённым способом и выберите файлы в настройках. Для запуска без скачивания: `SAMARIZATOR_SKIP_DOWNLOAD=1 ./start.sh` |
| Ошибка `whisper-cli` | Проверить `whisper-cli --help`, путь к GGML `.bin`, права чтения файла и язык. Установщик использует `brew install whisper-cpp` |
| Установил `large-v3`, но текст не изменился | Проверьте выбранный `.bin` в настройках и нажмите **«Распознать заново»**. «Распознать / продолжить» использует модель, сохранённую для старой записи |
| `large-v3` работает слишком медленно | Сравните с `large-v3-turbo` или `large-v3-q5_0` по [руководству по моделям](models.md). Уменьшение модели меняет компромисс скорости и качества |
| Сработала защита памяти | Выбрать меньшую модель или увеличить бюджет с запасом для macOS; нажать «Распознать / продолжить» |
| HTTP 401/403 | Проверить API-ключ, base URL и права аккаунта на выбранную модель |
| HTTP 404 | Указать **полный** путь API, не только домен и не адрес веб-чата |
| Ошибка сертификата / соединения | Проверить base URL и сеть. Сертификат проверяется по системному хранилищу macOS, поэтому корпоративный корневой CA из Keychain работает сам. Проверка TLS не отключается |
| Ответ обрезан | Уменьшить число символов на блок или увеличить лимит ответа, учитывая окно контекста модели |
| Неподдерживаемый JSON | Убедиться, что API возвращает `choices[0].message.content` со строкой JSON; выбрать модель, способную соблюдать формат |
| Изменился исходный файл | Вернуть исходный файл или импортировать изменённый как новую запись. Контрольная сумма намеренно блокирует смешивание версий |
| Obsidian не открывает заметку | Приложение берёт список хранилищ из конфига Obsidian и обращается к нужному по его идентификатору, поэтому имя папки и символические ссылки iCloud больше не мешают. Если ни одно зарегистрированное хранилище не содержит заметку, кнопка показывает, какие хранилища Obsidian знает, и предлагает открыть папку в Finder. Лечится так: Obsidian → «Открыть папку как хранилище» → выбрать папку из настроек. Просто существующей на диске папки недостаточно |
| Приложение прервано | Запустить снова: статус станет «Приостановлена». Нажать продолжение нужной стадии |
| В live-записи слышен только один источник | Запустить `.venv/bin/python -m samarizator.live <файл записи>` — покажет уровень по каждому каналу и устройство дорожки. См. раздел ниже |
| Live-запись системного звука пустая | Запустить `./scripts/diagnose_system_audio.sh` со включённым звуком — он перебирает варианты настроек ScreenCaptureKit и показывает, какой отдаёт аудио. См. раздел ниже |

## Системный звук: пустая запись

Сообщение появляется, когда в WAV не попало ни одного сэмпла. Включите звук (видео, музыку)
и выполните полную диагностику — она пересобирает helper, проверяет разрешение и прогоняет
пять вариантов настроек ScreenCaptureKit подряд, показывая, какой из них отдаёт звук:

```bash
./scripts/diagnose_system_audio.sh
```

Быстрая проверка только основного варианта, без перебора:

```bash
.venv/bin/python -m samarizator.screencapture check
```

Она запускает helper напрямую, минуя FFmpeg, и печатает три вещи: сколько байт прочитано,
сколько аудиобуферов насчитал сам helper и пиковый уровень. Дальше по результату:

Известный случай: на macOS 15.6.1 захват отдавал ноль буферов, пока helper регистрировал
выход `.screen`. Сейчас видеовыход не регистрируется; если в выводе строка `default` даёт
нули, а какой-то другой вариант — байты, пришлите таблицу целиком.

| Что напечатала диагностика | Что это значит |
|---|---|
| `Состояние:` про разрешение | macOS не дала доступ. Разрешение выдаётся приложению-хозяину: при запуске через `./start.sh` включать надо **Terminal**, а не Samarizator, и оно действует со следующего запуска — перезапустите приложение |
| Байт 0, буферов 0 | ScreenCaptureKit не отдаёт звук вообще. Пришлите журнал, путь печатается последней строкой |
| Буферы есть, пиковый уровень 0.000 | Захват работает, но в него приходит цифровая тишина: звук идёт мимо захватываемого выхода |
| Байты есть, уровень больше 0 | Захват исправен, потеря между helper'ом и FFmpeg — пришлите журнал записи из `recordings` |

Последним разделом диагностика печатает команды `afplay` для записанных фрагментов — так
можно убедиться на слух, что захвачен именно нужный звук. Фрагменты преобразуются в WAV
прямо в скрипте: набор опций для сырого PCM отличается между сборками FFmpeg (в ffplay 9
убран `-ac`), а WAV открывается любым проигрывателем.

Журнал helper'а после неудачной записи намеренно не удаляется: путь к нему приложение
показывает прямо в сообщении об ошибке.

Пока причина не найдена, системный звук можно получить запасным путём — через устройство
петли: в настройках «Захват системного звука» выберите «Устройство петли».

## Live: микрофон шумит при записи двух дорожек

Если микрофон в одиночной записи чистый, а в паре с системным звуком шумит, дело в сведении
дорожек, а не в устройстве. До 14 сентября 2026 каждая дорожка бралась как `pan=mono|c0=c0` —
только канал 0. У стереовхода, где голос не в левом канале, в запись попадала шумовая полка.
Сейчас применяется `aformat=channel_layouts=mono`, то есть то же сведение, что и `-ac 1` в
одиночном режиме, а выравнивание часов смягчено с `async=1000` до `async=1`.

Если шум остался, сравните варианты на своих устройствах — говорите в микрофон и держите звук
из приложений:

```bash
./scripts/diagnose_dual_audio.sh
```

Скрипт запишет по 10 секунд пятью способами (включая эталон «только микрофон» и старое
поведение), покажет уровни по дорожкам и напечатает команды `afplay` для прослушивания.
Профиль задаётся вручную: `python -m samarizator.live record --mix hard-sync --source both`.
Доступны `default`, `hard-sync`, `no-resample`, `legacy-pan`. Пришлите таблицу уровней и
впечатление на слух — по ним видно, виновато ли выравнивание часов.

Ещё одна причина треска — переполнение очереди у живого устройства: FFmpeg тогда отбрасывает
пакеты. Размер очереди поднят с 512 до 4096, а журнал записи теперь пишется с уровнем
`warning` и **сохраняется**, если FFmpeg что-то сообщил. Лежит рядом с записью в
`recordings/live-….log`.

## Микрофон шумит: обработка перед распознаванием

Браузер звучит чище не потому, что лучше пишет, а потому что обрабатывает: WebRTC включает
подавление эха, шумоподавление и автоусиление ещё до того, как вы услышите себя. Приложение
пишет устройство как есть, поэтому слышен реальный микрофон со всем шумом комнаты.

Обработку можно включить на своей стороне — **только для того, что слышит Whisper**. Запись на
диске не меняется, профиль можно переключить и распознать заново. Сначала сравните на своей
записи:

```bash
.venv/bin/python -m samarizator.live clean "путь/к/live-….wav"
```

Команда создаст рядом три файла (`.off.wav`, `.light.wav`, `.strong.wav`), напечатает уровень
речи, уровень пауз и разницу между ними, и даст команды `afplay` для прослушивания. Важна
именно разница: чем она больше, тем лучше речь отделена от шума.

На синтетическом образце (речь отрывками, шипение и гул 50 Гц) получилось: без обработки
7.9 дБ, `light` — 14.6 дБ, `strong` — 18.7 дБ. На вашей записи числа будут другими, поэтому
и нужна проверка.

| Профиль | Что делает | Когда брать |
|---|---|---|
| `off` | ничего | по умолчанию; звук и так чистый |
| `light` | срез гула ниже 80 Гц и выравнивание громкости речи | обычный кабинет, тихий микрофон |
| `strong` | то же плюс подавление широкополосного шипения | шумная комната; может смазывать тихую речь |

Выбирается в **Настройки → Качество и термины → «Обработка звука перед Whisper»**.

## Live: микрофон «дышит» — уровень приседает раз в несколько секунд

Это не шум, а пампинг: автоматическая регулировка усиления или подавление эха приглушает
микрофон, когда говорит другая сторона. В цепочке приложения таких обработок нет — ни гейта,
ни компрессора, FFmpeg пишет то, что отдаёт устройство. Значит источник снаружи.

Проверьте измерением:

```bash
.venv/bin/python -m samarizator.live profile "путь/к/live-….wav"
```

Команда печатает уровень каждой дорожки посекундно и считает, как часто микрофон проседает
именно в те секунды, когда громкая вторая сторона. Доля выше 40% — это внешнее подавление,
а не запись.

Что отключать, по убыванию вероятности:

1. **Динамики вместо наушников.** Любое подавление эха приглушает микрофон, пока слышно
   удалённую речь. Наушники убирают причину.
2. **Mic Mode в Пункте управления.** Во время записи откройте Пункт управления → «Режим
   микрофона» и поставьте «Стандартный». «Изоляция голоса» агрессивно вырезает всё, что
   считает не-речью, и как раз «дышит». Режим запоминается для каждого приложения.
3. **Автогромкость в Zoom/Teams.** «Автоматически регулировать громкость микрофона» и
   шумоподавление двигают общий уровень входа macOS — вашу запись это задевает напрямую.
   Отключите их в настройках звука клиента.
4. **Шумоподавление в системных настройках.** Системные настройки → Звук → Вход: снимите
   «Ambient noise reduction», если пункт есть, и держите уровень входа около 75%, а не на
   максимуме — на максимуме слышен каждый шорох.
5. **AirPods и Bluetooth-гарнитуры** переключаются в узкополосный режим и звучат заметно
   хуже проводного микрофона.

## Live: в записи слышен только один источник

Микрофон и системный звук пишутся в один файл разными каналами, поэтому на слух пропажу
одного источника легко спутать с тихим микшированием. Проверьте записанный файл:

```bash
.venv/bin/python -m samarizator.live "~/Library/Application Support/Samarizator/recordings/live-….wav"
```

Команда печатает RMS и пик по каждому каналу отдельно и называет устройство, с которого
шла дорожка. Дальше:

| Что видно | Что это значит |
|---|---|
| Канал 1 «тишина» | Микрофон не отдал звук. Проверьте, то ли устройство выбрано в настройках live-записи: в отчёте оно названо. Без явного выбора берётся первый вход AVFoundation, а он не всегда системный по умолчанию |
| Канал 2 «тишина» | Не дошёл системный звук — раздел про пустую запись выше |
| Оба канала со звуком, но в тексте один источник | Дело в уровнях, а не в захвате: сведение двух каналов в моно даёт каждому источнику вдвое меньшую амплитуду. Поднимите громкость тихого источника до начала встречи |

То же самое приложение показывает само после каждой live-записи с двумя дорожками, измеряя
первые 30 секунд. Если источник молчал в начале, предупреждение будет ложным — проверьте
командой выше по всему файлу.

## Без интернета после установки

Модели и пакеты должны быть установлены заранее. Запуск непосредственно из окружения не обращается к менеджеру пакетов:

```bash
.venv/bin/python -m samarizator.app
```

Распознавание работает офлайн. Для сводки нужен доступ к выбранному API; локальная LLM поддерживается через совместимый сервер на localhost (Ollama, LM Studio). Облачного распознавания речи нет.

## Особенности API

Пример полного URL Azure: `https://<resource>.openai.azure.com/openai/deployments/<deployment>/chat/completions?api-version=<supported-version>`. Версию API предоставляет ваша компания. Заголовок — `api-key`, префикс — пустой. Для стандартного шлюза обычно `Authorization` и `Bearer `.

Интерфейс передаёт `model`, `messages`, `temperature`, `max_tokens` и ждёт ключ в заголовке `Authorization: Bearer`. Если сервис использует другой протокол, OAuth, заголовок `api-key`, собственный CA или reasoning-модель без этих параметров, потребуется небольшой адаптер в `summary.py`.
