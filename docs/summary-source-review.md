# Сводки 2.5: проверка содержания по источнику

Предыдущая версия 2.4, по оценке пользователя, ухудшила результат. Конкретный неудачный
ответ модели и соответствующий транскрипт для анализа не предоставлены. Поэтому причины
семантического ухудшения не считаются доказанными; ниже перечислены проверяемые изменения.

## Что меняется

1. Системный промпт задаёт порядок: верность источнику, полнота существенного, понятность,
   затем краткость. Убрана обязательная схема из четырёх звеньев для каждой мысли.
2. Подробное извлечение сохраняет самостоятельные темы, аргументы, примеры, альтернативы,
   условия, ограничения и неопределённость. Упоминание один раз не повод исключать тему.
3. Краткая сводка сохраняет до 9 тезисов, но больше не ограничивает тезис 300 символами
   и обзор одним предложением. Размер ответа по-прежнему ограничен настройками API
   и защитными пределами JSON; важные детали должны остаться в подробном варианте.
4. На границах блоков передаются соседние **исходные** реплики с настоящими ID,
   а не сгенерированный пересказ прошлого блока. Это помогает понимать отсылки и условия.
5. После извлечения выполняется дополнительный запрос: модель видит исходный текст
   и черновик, проверяет полноту и фактическую точность, возвращает исправленный результат.
6. Только затем строятся реестр, итог по решениям и краткая сводка. Подробный реестр
   сохраняет пункты всех обработанных блоков и не проходит через краткое сжатие.

## Контроль проверки

Выход проверки использует обычный JSON сводки с дополнительными полями:

- `draft_ids` в каждом пункте: индексы исходных пунктов черновика, которые сохранены,
  исправлены или объединены. Для добавленных пунктов — пустой список.
- `removed`: явные удаления с индексом исходного пункта, причиной и реальными ID evidence.
- Каждый исходный пункт должен быть учтён ровно один раз. Ответ без учёта части пунктов,
  с дублированным учётом или с выдуманными ID отклоняется и повторяется до трёх попыток.
- Ссылки на соседние реплики допустимы для контекста, но каждый содержательный пункт
  должен ссылаться хотя бы на один сегмент основного блока.
- В последующие запросы, GUI и экспорт поля учёта не передаются. Они сохраняются вместе
  с первоначальным черновиком в локальных checkpoints для диагностики.

Это проверка структуры и происхождения пунктов, **не доказательство истинности** текста.
Модель всё ещё может неверно интерпретировать источник или удалить полезный пункт с ошибочным
объяснением. Именно поэтому сохранены черновик и ответ проверки, нужен контроль на реальных данных.

## Лимиты, стоимость и восстановление

Для основного текста отводится половина `input_chars`; для контекста с каждой стороны —
не более 1200 символов и не более 10% `input_chars`. В контексте длинная реплика может
передаваться как помеченный отрывок; в основных блоках весь текст сохраняется.
Данные проверки (исходник + черновик) также должны помещаться в `input_chars`.
Инструкции SYSTEM и этапа идут дополнительно, как и ранее: лимит символов данных не равен
токенному окну модели. Потребление RAM по-прежнему ограничивается существующим watchdog.

Если весь черновик не помещается, проверка делится на группы пунктов с тем же исходником.
В таком случае проверяется точность переданных пунктов, а повторный поиск всех пропусков
по блоку не заявляется выполненным. Если даже один пункт вместе с источником не помещается,
сохраняется черновик с предупреждением о незавершённой проверке.

При ошибке/обрезании/некорректной структуре проверки исходное извлечение не выбрасывается.
В обеих сводках и в Obsidian появляется пометка о незавершённой проверке. Следующий запуск
использует сохранённый черновик и снова пробует проверку. Успешные проверки кэшируются.
Остановка процесса оставляет ранее завершённые блоки. Данные не уходят на запасной API.

Обычный блок теперь требует извлечения и проверки; дополнительно остаются запросы
согласования решений и краткого синтеза. На длинной записи блоков больше, чем в 2.4;
суммаризация может ощутимо подорожать и замедлиться. Лимит ответа и выбранная модель
автоматически не меняются: допустимые значения зависят от корпоративного провайдера.

## Что проверено

В `tests/test_summary_source_review.py`:

- передача соседних реплик с сохранением всего основного текста и ограничением размера;
- обработка исправленного статуса и добавленного условия через HTTP mock;
- защита от потери одного из двух пунктов, даже если evidence у них одинаковый;
- неверные ссылки, повторный учёт, пустой ответ и сбой сети;
- сохранение предупреждения в GUI/Obsidian и повтор проверки без повторного извлечения;
- разбиение большого черновика и запрет подмены темы только соседним контекстом;
- явное удаление выдуманного утверждения с сохранением причины в checkpoint.

Полный набор: 88 тестов, Ruff, git diff --check. Модель в тестах подменена.
Качество и скорость реального корпоративного API не измерены. Сравнивать нужно на одном
транскрипте и одинаковой модели, включая поздние отмены и возврат к теме через несколько блоков.
Контекст соседей ограничен; это не глобальная память всей встречи. Возможны повторы между блоками.

## Как применить

Закрыть приложение, обновить `quality-m4-dual-summaries`, запустить `./start.sh` и снова
нажать «Создать сводку». Аудио заново распознавать не нужно. В заголовке — «Сводки 2.5».
Сохранённые сводки сами не переписываются при запуске. Изменение промптов и входа приводит
к пересчёту checkpoints суммаризации только при явном повторном создании сводки.
