## Среда разработки — главное ограничение

Ассистент работает в Linux-контейнере. **Swift-тулчейна и macOS SDK нет,
`swift build` невозможен.** Собирает и проверяет только автор, на своём MacBook.

Следствия:
- каждая ошибка компиляции стоит круга «пуш → сборка у автора → лог ошибки → правка»;
- перед пушем обязательно искать по проекту ссылки на переименованные символы —
  компилятор их не поймает, а круг стоит дорого;
- писать только те API, в которых есть уверенность.

## Грабли, на которые уже наступали

1. **`#Preview` валит сборку.** Макрос реализован плагином Xcode (`PreviewsMacros`),
   при `swift build` из терминала его нет. Превью в проекте не использовать.
2. **`deinit` у `@MainActor`-класса** выполняется вне актора и НЕ может обращаться
   к изолированным свойствам. Для отменяемых задач есть `Character/TaskBag.swift` —
   Sendable-контейнер в `let`-свойстве. Токен монитора мыши по той же причине
   лежит в `MonitorBox` внутри `MouseTracker`.
3. **Код верхнего уровня в `main.swift` НЕ изолирован** на главном акторе.
   Создание `@MainActor`-делегата обёрнуто в `MainActor.assumeIsolated`.
4. **Классы уровня AppKit нуждаются в явном `@MainActor`.** `AppDelegate` и
   `NotchWindowController` помечены; SwiftUI-вью получают изоляцию сами, через
   протокол `View` — отсюда иллюзия, что можно без пометки.
5. **Матовое стекло (`NSVisualEffectView`, `.behindWindow`) не заработало.**
   Ни внутри SwiftUI (обрезка через `clipShape` уводит вью в отдельный слой и
   убивает размытие фона), ни как `contentView` панели с собственным `maskImage`.
   Неисключённый подозреваемый — уровень окна `.screenSaver`. Код удалён,
   капсула сплошная чёрная. Если возвращаться к идее — начинать с уровня окна.
6. **Приложение внешне неотличимо от незапустившегося.** Капсула чёрная, по
   размеру выреза. Поэтому есть `FOCUS_DEBUG=1` (красная увеличенная капсула) и
   печать метрик при старте. Запускать бинарник из терминала: `open` не передаёт
   переменные окружения.
7. **Глобальный монитор мыши слепнет над собственным окном.** Как только панель
   раскрывается и перестаёт пропускать мышь, `NSEvent.addGlobalMonitorForEvents`
   перестаёт видеть курсор. Поэтому ховер определяется опросом
   `NSEvent.mouseLocation` по таймеру (`HoverDetector`), и тот же опрос питает
   слежение глаз при раскрытии.
8. **Саккады без паузы читаются как тревожность.** Первая версия запускала их
   каждые ~0.9 сек, пока курсор неподвижен. Нужна случайная пауза между ними.

## Фаза 4а — решения и непроверенные места

В отличие от раздела «Грабли» выше, это НЕ подтверждено сборкой — здесь
зафиксированы решения и места, за которыми стоит следить в первую очередь
при первом запуске на живой машине.

- **Фокус текстового поля.** `NotchPanel` получила
  `becomesKeyOnlyIfNeeded = true` (штатное `NSPanel`-свойство: панель
  становится key-окном только когда вью внутри реально запрашивает
  firstResponder — то есть клик в текстовое поле, а не в чекбокс). Поверх —
  собственный флаг `allowsKeyWhenExpanded`, который `NotchWindowController`
  включает только пока панель раскрыта, и явно снимает фокус
  (`resignKey()` + `makeFirstResponder(nil)`) при сворачивании. Если на
  живой машине ввод текста не заработает — это первое место для проверки
  (см. также раздел «Где что крутить» ниже, `Window/NotchPanel.swift`).
  Если система при фокусе поля всё же выводит приложение на передний план
  сильнее, чем нужно (например, крадёт Cmd+Tab или меню-бар) — заявленный
  критерий приёмки требует отката интерактивности поля, а не полумер.
- **SwiftData через голый `ModelContext`, не `@Query`.** `TaskStore` сам
  вызывает `context.fetch(...)` после каждой мутации, а не подписывается на
  среду через `@Query` в SwiftUI-вью. Причина — `ExpandedPanelView` живёт
  внутри вручную созданного `NSHostingView` без `App`/`Scene`-лайфцикла
  SwiftUI, и поведение `@Query` в такой конфигурации никем не проверялось.
  Если на живой машине список задач не обновляется после добавления/
  выполнения — искать здесь, а не в UI-слое.
- **`#Predicate` и `SortDescriptor` по `Date`/`Bool`.** Синтаксис в
  `TaskStore.swift` — стандартный из документации Apple, но ни разу не видел
  компилятор. Особое внимание — сортировке (используется только `createdAt`,
  не `completedAt`, чтобы не полагаться на `SortDescriptor` по опциональному
  `Date?`).
- **Путь хранения БД.** `PersistenceConfig` кладёт файл в
  `~/Library/Application Support/dev.samarizator.focuscompanion/FocusCompanion.sqlite`
  явным `URL`, а не полагается на путь по умолчанию — приложение собирается
  вручную (`build-app.sh`), Xcode-проекта нет. Если приложение падает при
  старте с ошибкой контейнера — вероятно, здесь (права на директорию,
  формат конфигурации).

## Проверенная геометрия (MacBook автора)

```
экран 1728 x 1117
вырез 185 x 32, safeAreaInsets.top = 32
высота меню-бара 38  (меню-бар на 6pt глубже выреза)
auxiliaryTopLeftArea.width = 771, auxiliaryTopRightArea.width = 772
```

Определение выреза: `hasNotch` = обе auxiliary-области не nil;
ширина = ширина экрана минус обе области; высота = `safeAreaInsets.top`.
На экранах без выреза — виртуальная капсула, высота = высота меню-бара.

## Текущая посадка персонажа

- Тело свёрнутой капсулы начинается от **левого** края выреза и поглощает его,
  продолжаясь вправо на `collapsedExtensionRight` (62pt). Если начинать от
  правого края, у стыка видно скругление капсулы — шов.
- Высота свёрнутой капсулы = высоте выреза, она не свисает под меню-бар.
- Окно панели всегда в размере раскрытого состояния и центрировано **по вырезу**:
  анимировать `setFrame` синхронно со SwiftUI-анимацией — источник рывков.
- Глаза позиционируются относительно центра ОКНА, а не капсулы, чтобы при
  раскрытии не ездить по горизонтали.

## Где что крутить

- `Config/AppearanceConfig.swift` — геометрия капсулы, размеры раскрытой панели,
  задержки ховера.
- `Config/CharacterConfig.swift` — всё про персонажа: размер и форма глаз,
  пружина слежения, моргание, саккады, дыхание, debug-масштаб.
- `State/StateAppearance.swift` — как выглядит каждое эмоциональное состояние.

## Тон персонажа — требование, не украшение

У людей с СДВГ повышена чувствительность к критике. Поэтому:
- раздражение персонажа самоироничное и игровое («я тут с ума схожу от скуки»),
  НЕ обвиняющее («ты опять ничего не сделал»);
- никакого стыда, счётчиков провалов, «стриков», которые рвутся;
- позитивная реакция на выполнение ярче, чем негативная на просрочку;
- «сжигание» задачи — осознанное отпускание без вины. В UI «отпускаем»,
  а не «провалено».
