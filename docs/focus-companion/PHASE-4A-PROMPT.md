# ФАЗА 4а — Задачи: модель данных и три слота

## Контекст

macOS-приложение **Focus Companion** для людей с СДВГ. Фазы 1-3 завершены и
приняты автором на живой машине. Перед работой ОБЯЗАТЕЛЬНО прочитать
`docs/focus-companion/HANDOFF.md` — там грабли, на которые уже наступали, и
проверенная геометрия. Повторное наступание стоит круга сборки у автора.

Сейчас работает: капсула у выреза с живыми глазами, раскрытие по ховеру,
машина состояний эмоций с debug-меню.

**Цель Фазы 4а: задачи появляются, хранятся и живут в раскрытой панели.**

Фаза 4 разрезана на три части. Здесь делается ТОЛЬКО первая:
- **4а (эта)** — модель данных, три слота, список, чекбокс выполнения.
- 4б — механика сжигания (фитиль, таймер, исчезновение). НЕ делать.
- 4в — напоминания с учётом бездействия. НЕ делать.

Причина реза: модель данных потом несёт на себе и сжигание, и напоминания, и
Фазу 5 (интеграция с samarizator). Ошибка здесь дороже всего, поэтому она
делается отдельно и проверяется отдельно.

## Что сделать

### Модель

SwiftData-модель `CompanionTask`:
- текст задачи;
- дата создания;
- состояние: активна / выполнена;
- дата выполнения (опционально);
- **поле под будущий «фитиль»** (опциональная дата, до которой задача живёт) —
  само сжигание в 4б, но поле заложить сейчас, чтобы не мигрировать схему.

Имя `Task` НЕ использовать: оно конфликтует с `Swift.Task`, который в проекте
активно применяется (`TaskBag`, циклы моргания и саккад).

### Хранилище

- `ModelContainer` создаётся один раз и живёт на уровне приложения.
- Приложение запускается из собранного вручную `.app`-бандла (см. `build-app.sh`),
  без Xcode-проекта — проверь, что путь хранилища от этого не страдает. Если
  SwiftData по умолчанию кладёт базу в непредсказуемое место, задать URL явно,
  в `Application Support`, по bundle id `dev.samarizator.focuscompanion`.
- Данные обязаны переживать перезапуск. Это критерий приёмки.

### Правило трёх слотов

Максимум **3 активные** задачи одновременно. Выполненные в счёт не идут.

При попытке добавить четвёртую — персонаж предлагает сначала закрыть или
отпустить одну. В 4а достаточно понятного сообщения в панели; механики
отпускания ещё нет (она в 4б), поэтому формулировка не должна обещать кнопку,
которой пока не существует.

Тон обязателен (см. HANDOFF.md): это не ошибка и не выговор, а забота —
«трёх хватит, давай сначала разберёмся с этими». Никакого «вы превысили лимит».

### UI в раскрытой панели

`UI/ExpandedPanelView.swift` сейчас заглушка — заменить содержимым:
- список активных задач с чекбоксом выполнения;
- поле ввода новой задачи;
- выполненные задачи: показывать ли их и как — на твоё усмотрение, но они не
  должны копиться и превращать панель в свалку.

**Ввод текста потребует пересмотра одного решения Фазы 1.** У панели
`canBecomeKey = false` — она не забирает фокус. Для текстового поля фокус
нужен. Решение: разрешить `canBecomeKey` ТОЛЬКО когда панель раскрыта, и
только пока идёт ввод. Свёрнутая панель обязана остаться неспособной
перехватить фокус — иначе персонаж начнёт красть фокус у того, с чем работает
пользователь, а это ровно то, чего мы избегали с Фазы 1.

Если сделать это надёжно не получается — НЕ ломай существующее поведение:
оставь ввод неработающим, честно опиши проблему в отчёте, и автор решит.
Работающий персонаж без ввода лучше, чем персонаж, ворующий фокус.

### Реакция персонажа на события

Использовать уже готовую `CompanionStateMachine`:
- задача выполнена → `.celebrating` на несколько секунд, потом обратно в `.idle`;
- задача добавлена → короткая реакция на усмотрение, но заметная.

Позитив должен быть ярче негатива — это прямое требование автора.

### Размеры панели

`expandedWidth`/`expandedHeight` (320 × 200) — заглушки из Фазы 3, не
подбирались под контент. Подогнать под список из трёх задач с полем ввода.
Числа оставить в `AppearanceConfig`.

## Чего НЕ делать

- Механику сжигания и фитиль (4б).
- Напоминания и отслеживание бездействия (4в).
- Интеграцию с samarizator (Фаза 5).
- Ничего за пределами `focus-companion/` и `docs/focus-companion/`.

## Среда: собрать невозможно

Linux-контейнер, Swift-тулчейна и macOS SDK нет. `swift build` не выполнять,
сборку не имитировать, о её успехе не заявлять. Автор собирает у себя.

Особое внимание: **SwiftData — самая рискованная часть проекта на данный
момент**, потому что её поведение (макросы `@Model`, контейнер, контекст) без
компилятора не проверить вообще никак. Используй минимальный, самый
общеупотребительный набор API. Не изобретай.

Перед пушем обязательно проверить поиском по проекту, что нет ссылок на
переименованные символы — компилятор их не поймает, а круг сборки дорог.
