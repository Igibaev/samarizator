# Focus Companion — Фаза 4в

Маленький персонаж, живущий в вырезе (notch) MacBook. Фаза 1 сделала
фундамент: borderless-окно над вырезом со статичной капсулой. Фаза 2 добавила
в капсулу живые глаза: слежение за курсором, моргание, саккады, едва заметное
дыхание. Фаза 3 добавила раскрытие капсулы по наведению курсора и машину
состояний эмоций, переключаемую вручную из debug-меню. Фаза 4а добавила
задачи: JSON-хранилище (`Model/TaskPersistence.swift`), правило трёх активных
слотов, список с чекбоксом выполнения и поле ввода в раскрытой панели. Фаза
4б добавила «сжигание» — фитиль, по истечении которого задача отпускается
сама, без вины и без укора. Фаза 4в добавила напоминания с учётом
бездействия — персонаж напоминает о задачах, только когда пользователь
отошёл/залип, а не во время активной работы, и не чаще, чем раз в кулдаун.

Подробности задач — в `docs/focus-companion/PHASE-1-PROMPT.md`,
`docs/focus-companion/PHASE-2-PROMPT.md`,
`docs/focus-companion/PHASE-3-PROMPT.md`,
`docs/focus-companion/PHASE-4A-PROMPT.md`,
`docs/focus-companion/PHASE-4B-PROMPT.md` и
`docs/focus-companion/PHASE-4C-PROMPT.md`.

## Требования

- macOS 14+
- Xcode / Swift-тулчейн (для `swift build`)

## Сборка и запуск

```bash
./build-app.sh
```

Скрипт:
1. собирает executable через `swift build -c release`;
2. вручную упаковывает бинарник в `FocusCompanion.app` (создаёт
   `Contents/MacOS`, кладёт `Info.plist`);
3. открывает получившийся `.app` через `open`.

Xcode-проект (`.xcodeproj`) сознательно не генерировался — его формат плохо
пишется и проверяется руками без Xcode под рукой.

## Как закрыть

У приложения нет иконки в Dock и пункта в Cmd+Tab (см. ниже). Выйти можно
через иконку-кружок в меню-баре → пункт **«Выход»**.

## Debug-режим и подбор параметров

Обычный режим невозможно оценить глазами (капсула чёрная и ровно по размеру
выреза, глаза — детали в десятки pt) — поэтому есть debug-режим:

```bash
FOCUS_DEBUG=1 swift run
```

В нём капсула красная, вытянута вниз из-под выреза, а персонаж внутри —
увеличен (ориентир ×3) и сдвинут ниже, чтобы моргание и саккады было видно
в деталях. Обычный режим (без переменной) эти правки не затрагивают.

При старте (в любом режиме) приложение печатает в терминал диагностику:
геометрию всех экранов и итоговый фрейм капсулы с учётом расширений
Фазы 2 — по этим цифрам удобно сверяться при подборе параметров.

**Все числа живости персонажа — в одном месте:**
`Sources/FocusCompanion/Config/CharacterConfig.swift`. Там же комментарии,
что каждый параметр делает и в каких пределах разумно его крутить: размер и
цвет глаз/зрачков, жёсткость пружины слежения, интервалы и длительность
моргания, амплитуда и тайминги саккад, период и амплитуда дыхания.
Расширение самой капсулы относительно физического выреза (ширина/глубина) —
в `Sources/FocusCompanion/Config/AppearanceConfig.swift`.

Правка логики (ViewModel/View) для подбора параметров не нужна — только эти
два конфига.

## Что сделано в Фазе 1

- Панель (`NSPanel`, borderless, non-activating) позиционируется точно над
  физическим вырезом экрана и рисует статичную чёрную капсулу.
- Капсула визуально продолжает вырез: верхние углы скруглены "наружу"
  (вогнутой кривой, как скругление корпуса вокруг камеры), нижние — обычным
  скруглением внутрь.
- Панель никогда не становится key/main-окном и не перехватывает клики
  (`ignoresMouseEvents = true`) — меню-бар под капсулой и вокруг неё
  полностью кликабелен.
- Приложение работает без Dock-иконки и без записи в Cmd+Tab
  (`LSUIElement` в `Info.plist` **и** `setActivationPolicy(.accessory)` в
  коде — на случай запуска голого бинарника без бандла).
- Поддержаны три конфигурации экрана:
  - MacBook с вырезом — капсула точно над вырезом;
  - MacBook без выреза / внешний монитор — виртуальная капсула по центру
    верхнего края экрана шириной из `AppearanceConfig`.
- При смене набора экранов (`didChangeScreenParametersNotification`:
  подключение/отключение монитора, смена разрешения) панель переезжает на
  экран с курсором мыши (или на `NSScreen.main`, если курсор не определить).
- Выход из приложения — через пункт «Выход» в меню NSStatusItem.

## Что сделано в Фазе 2

- Капсула расширена относительно физического выреза (`AppearanceConfig`:
  `capsuleExtraWidthPerSide`, `capsuleExtraDepth`) — верхний край и
  центрирование не тронуты, форма капсулы статична, как в Фазе 1.
- Пара живых глаз (`EyeView`/`EyesView`) поверх капсулы:
  - **слежение за курсором** — зрачки едут за глобальной позицией мыши
    (`MouseTracker` на `NSEvent.addGlobalMonitorForEvents`) с пружинной,
    не линейной, анимацией и мёртвой зоной у центра;
  - **моргание** — случайный интервал 3-7 сек, быстрое схлопывание высоты
    глаза (не веко-прямоугольник поверх), изредка двойное моргание;
  - **саккады** — после нескольких секунд неподвижности курсора зрачок
    резко отклоняется в случайную сторону и мягко возвращается обратно
    (несимметрично: рывок быстрый, возврат медленный);
  - **дыхание** — едва заметная пульсация масштаба ТОЛЬКО пары глаз, не
    капсулы (капсула жёстко привязана к вырезу, см. `EyesViewModel`).
- Вся логика живости — в `EyesViewModel` (`@Observable`, `@MainActor`,
  таймеры на `Task`/`Task.sleep`, честная случайность через
  `Double.random(in:)`, без псевдо-паттернов).
- Debug-режим (`FOCUS_DEBUG=1`) дополнительно увеличивает и сдвигает вниз
  персонажа (`CharacterConfig.debugScale`/`debugYOffset`), чтобы моргание и
  саккады было видно в деталях; `AppDelegate.logDiagnostics` печатает
  итоговый фрейм капсулы с учётом новых расширений.
- Ничего из Фаз 3-5 (раскрытие по ховеру, эмоции, задачи) не делалось —
  панель по-прежнему `ignoresMouseEvents = true`, `canBecomeKey = false`.

## Что сделано в Фазе 3

- **Раскрытие по ховеру.** Панель (`NSPanel`) теперь ВСЕГДА создаётся в
  размере раскрытого состояния (`AppearanceConfig.expandedWidth/Height`) —
  морфится только содержимое внутри неё (размер и радиусы капсулы,
  положение глаз), а не сам фрейм окна: два независимых механизма анимации
  (AppKit `setFrame` и SwiftUI) с разными таймингами дают рывки, поэтому их
  разделили.
- **`HoverDetector`** (`Interaction/HoverDetector.swift`) определяет
  наведение не через `NSTrackingArea`/глобальный монитор, а опросом
  `NSEvent.mouseLocation` (~20 Гц, `AppearanceConfig.hoverPollInterval`):
  это единственный способ, одинаково работающий и когда панель пропускает
  клики (свёрнуто), и когда перехватывает их (раскрыто, для будущих
  чекбоксов Фазы 4). Задержки перед раскрытием (~0.2с) и сворачиванием
  (~0.15с) гасят случайный пролёт курсора мимо и дрожание у границы.
- **`NotchWindowController`** переключает `NSPanel.ignoresMouseEvents` по
  колбэку `HoverDetector.onExpansionChange` — свёрнуто: `true` (меню-бар
  под капсулой кликабелен, критерий приёмки Фазы 1), раскрыто: `false`.
- Тот же 20 Гц опрос `HoverDetector` во время раскрытия питает и слежение
  глаз — глобальный монитор мыши (`MouseTracker`) в этот момент слепнет,
  потому что курсор оказывается над собственным окном приложения.
- **Машина состояний эмоций** (`State/CompanionState.swift`,
  `State/StateAppearance.swift`, `State/CompanionStateMachine.swift`):
  7 состояний (`idle`/`listening`/`thinking`/`reminding`/`annoyed`/
  `celebrating`/`burning`), каждое — набор визуальных множителей
  (форма/размер/наклон глаз, цвет и сила подсветки, темп дыхания/моргания/
  саккад). `CompanionStateMachine` не заводит собственных таймеров — она
  публикует целевые параметры, а `EyesViewModel` читает их множителями при
  планировании уже существующих циклов.
- **Debug-меню** статус-айтема `FC` получило подменю «Состояние (debug)» со
  всеми состояниями и галочкой у текущего — критерий приёмки Фазы 3.
- `.celebrating` получил новую форму глаз — дуги-полумесяцы (`EyeShape.crescent`
  в `Character/EyeView.swift`) вместо обычной щели.
- `.annoyed` — сознательно самоироничное, игровое раздражение (скучающий
  прищур, подчёркнутые "вздохи"), а не укор пользователю; по амплитуде и
  яркости подсветки заметно слабее `.celebrating` — позитив громче негатива,
  прямое требование автора (см. `State/StateAppearance.swift`).
- `UI/ExpandedPanelView.swift` — заготовка контента раскрытой панели под
  "головой" персонажа (подпись состояния + плейсхолдер), чтобы пустая
  область не выглядела как ошибка отрисовки. Список задач — Фаза 4.

## Что сделано в Фазе 4а

- **`CompanionTask`** (`Model/CompanionTask.swift`) — обычная
  `Codable`-структура, НЕ SwiftData-модель (макросы Apple вроде `@Model` не
  работают при сборке через `swift build` из терминала, см. HANDOFF.md):
  текст, дата создания, флаг выполнения, дата выполнения, плюс задел на
  будущее — опциональное поле `fuseDate` под «фитиль» механики сжигания
  (Фаза 4б), чтобы не менять формат файла отдельным кругом. Имя `Task` не
  используется — конфликтует со `Swift.Task`, которым активно пользуется
  `TaskBag`.
- **`Model/TaskPersistence.swift`** читает и пишет задачи целиком одним
  JSON-файлом в `~/Library/Application Support/dev.samarizator.focuscompanion/tasks.json`
  — путь задан явно, а не отдан фреймворку: приложение собирается вручную
  (`build-app.sh`, без Xcode-проекта) и может запускаться голым бинарником.
  Запись атомарная (`.atomic`) — недописанный JSON означал бы потерю всех
  задач разом.
- **`Model/TaskStore.swift`** — CRUD поверх массива в памяти, целиком
  перезаписываемого в JSON при каждом изменении, и правило трёх активных
  слотов; выполненные задачи не копятся — ретенция на последние 8.
- **`Model/TaskPanelController.swift`** связывает `TaskStore` с
  `CompanionStateMachine`: выполнение задачи → `.celebrating` на несколько
  секунд и обратно в `.idle`; добавление задачи → короткая реакция
  (`.listening`), заметно короче и слабее праздничной — позитив должен быть
  ярче негатива, это касается и длительности реакций.
- **`UI/ExpandedPanelView.swift`** — список активных задач с чекбоксом,
  поле ввода новой задачи, заботливое сообщение при заполненных трёх слотах
  («Трёх задач хватит — давай сначала разберёмся с этими», без обещания
  кнопки отпускания — той ещё нет) и счётчик выполненных без самого списка.
- **Фокус текстового поля** (`Window/NotchPanel.swift`): панель получила
  `becomesKeyOnlyIfNeeded = true` — штатный AppKit-механизм для панелей,
  благодаря которому она становится key-окном ТОЛЬКО когда текстовое поле
  реально запрашивает первого respondera, а не от любого клика. Сверху —
  собственный флаг `allowsKeyWhenExpanded`, который `NotchWindowController`
  включает/выключает синхронно со свёрнутым/раскрытым состоянием: свёрнутая
  панель гарантированно не может стать key ни при каких условиях (критерий
  Фазы 1). При сворачивании фокус явно снимается (`resignKey()` +
  `makeFirstResponder(nil)`), а SwiftUI-фокус поля сбрасывается через
  `@FocusState`, отслеживающий `hoverDetector.isExpanded`.
- `AppearanceConfig.expandedWidth/Height` подогнаны под список из трёх задач
  и поле ввода (300×210 вместо заглушки 320×200 из Фазы 3).

## Что сделано в Фазе 4б

Механика «сжигания» — осознанное отпускание задачи без вины (не просрочка,
не наказание; см. HANDOFF.md, «Рамка смысла»).

- **Поджиг фитиля** — значок у строки задачи (`ExpandedPanelView.fuseControl`).
  Негорящая задача: значок открывает `Menu` из трёх пресетов длительности
  (`FusePreset` — 15 минут, час, до конца дня); поджиг ВСЕГДА идёт через
  явный выбор пункта, а не одиночный клик, потому что финал (в отличие от
  самого поджига) необратим. Горящая задача: тот же значок гасит фитиль
  одним тапом без подтверждения — «передумал» не требует церемонии.
- **`Model/FusePreset.swift`** — три пресета. «До конца дня» — единственный
  без фиксированного числа секунд: считается от момента поджига до
  ближайшей полуночи по календарю пользователя.
- **`Model/TaskStore.swift`** — `igniteFuse`/`extinguishFuse`/`releaseBurnedOut`.
  Догоревшая задача не помечается «выполненной» — она целиком уходит из
  хранилища, минуя список выполненных и любую статистику (никаких счётчиков
  отпущенных задач).
- **Общий таймер горения** — один на ВСЕ горящие задачи разом
  (`TaskBag.Key.burnTicker` в `TaskPanelController`, тик раз в секунду), не
  по таймеру на задачу.
- **Полоска остатка фитиля** в строке задачи — без единой цифры секунд/минут,
  считается на лету от `CompanionTask.fuseDate`/`fuseStartedAt` и текущего
  момента (`TaskPanelController.now`, обновляется тем же тиком).
- **`.burning` — фоновое состояние**, как второй `.idle`: пока горит хотя бы
  одна задача, персонаж оседает в `.burning`, иначе — в `.idle`; временные
  реакции (`.celebrating`/`.listening`) его не перекрывают и, отыграв,
  возвращаются в актуальное на тот момент фоновое состояние, а не жёстко в
  `.idle` (`TaskPanelController.syncAmbientState`/`scheduleReturnToRestingState`).
- **Догорание** — реакция персонажа сознательно БЕЗ отдельной анимации:
  задача тихо исчезает из списка, персонаж оседает в `.idle`/`.burning`.
  Решение и его обоснование — в HANDOFF.md, раздел «Фаза 4б — решения».
- **Приложение было закрыто, пока фитиль горел** — обязательный случай.
  `TaskStore.init` отпускает догоревшие задачи тихо, ДО того как до них
  доберётся UI или машина состояний: без эмоций персонажа и без сообщения о
  пропущенном.

## Что сделано в Фазе 4в

Напоминания с учётом бездействия — персонаж напоминает о задачах, не дёргая
во время работы (прямое требование автора).

- **`Input/IdleTimeProvider.swift`** — обёртка над
  `CGEventSource.secondsSinceLastEventType(.combinedSessionState, eventType:)`
  с самодельной константой "любой тип события" (`kCGAnyInputEventType`,
  собрана из `rawValue`, Swift не экспортирует её по имени) — секунды с
  последнего ЛЮБОГО ввода (мышь/клавиатура/трекпад) во всей системе, БЕЗ
  разрешений Accessibility. Это ключевое требование: просить у пользователя
  доступ к клавиатуре ради напоминалки недопустимо. Место наименьшей
  уверенности во всей Фазе 4в — не проверено компилятором, запасной вариант
  (минимум по конкретным типам событий) описан прямо в файле.
- **`Model/TaskPanelController.swift`** — `startReminderTicker`/
  `tickReminder`/`isQuietHour`: общий опрос детектора бездействия раз в 30
  секунд (`TaskBag.Key.reminderTicker`, НЕ второй параллельный таймер горения
  — своя запись в уже существующем `TaskBag`). Напоминание показывается
  (`.reminding` на несколько секунд, затем персонаж сам возвращается в
  актуальное фоновое состояние через уже существующий
  `scheduleReturnToRestingState`) только если: есть хотя бы одна активная
  задача; человек только что впервые залип (бездействие впервые превысило
  порог) ИЛИ только что вернулся после залипания (бездействие только что
  сброшено в ноль); сейчас не ночь (23:00-08:00 по умолчанию); с прошлого
  напоминания прошёл кулдаун (25 минут по умолчанию); персонаж не занят
  другой временной реакцией (`.celebrating`/`.listening`).
- **`Config/CharacterConfig.swift`** — все пороги напоминаний одним местом:
  `reminderIdleThreshold`, `reminderCooldown`, `reminderDisplayDuration`,
  `reminderTickInterval`, `reminderQuietHourStart/End`.
- **Без нового пользовательского текста.** `.reminding` — визуальное
  состояние (уже существующая мягкая жёлтая пульсация подсветки из Фазы 3),
  одного взгляда персонажа достаточно; текста в диалогах напоминания в этой
  фазе нет — осознанный выбор, см. отчёт к коммиту.
- Идея "во время активной работы саккады реже" из PHASE-4C-PROMPT.md
  сознательно НЕ реализована (задание явно разрешает пропустить при
  сомнении) — см. отчёт к коммиту.

## Важно: сборка не проверялась

Код писался в Linux-контейнере без Swift-тулчейна и macOS SDK —
`swift build` / `xcodebuild` здесь физически невозможны. Сборка и запуск
**не проверялись** ни разу — ни в одной из Фаз 1-4в. Первый запуск на
реальном Mac обязателен, и скорее всего потребуются мелкие правки — см.
список неуверенных мест в HANDOFF.md и в отчёте, приложенном к коммиту.
